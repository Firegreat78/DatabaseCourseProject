# Биржа ценных бумаг — backend

Серверная часть системы учёта биржевых операций: клиенты открывают брокерские и
депозитарные счета, подают заявки на покупку и продажу ценных бумаг, сотрудники
верифицируют паспортные данные и обрабатывают заявки. Курсовой проект по базам
данных.

## Архитектура

Бизнес-логика вынесена в базу данных, а не в приложение. Движение денег,
резервирование средств, исполнение заявок и списание бумаг реализованы 35
функциями и 16 процедурами на PL/pgSQL. FastAPI отвечает только за
аутентификацию, валидацию входных данных и транспорт.

Следствия такого решения:

* операция целиком выполняется в одной транзакции на стороне СУБД — приложение
  не может оставить систему в промежуточном состоянии;
* инварианты (неотрицательный баланс, корректность сумм заявок, валидность
  реквизитов) обеспечены триггерами и ограничениями, поэтому ни один маршрут
  приложения не может их нарушить;
* процедуры не выбрасывают исключения наружу, а возвращают текст ошибки через
  `OUT p_error_message`; слой FastAPI транслирует его в HTTP-ответ.

Цена решения — логика непереносима на другую СУБД и слабо покрывается
модульными тестами.

## Стек

* Python 3.14, FastAPI, Uvicorn
* SQLAlchemy 2.0 (async) + asyncpg
* PostgreSQL
* Pydantic v2 — схемы запросов и ответов
* JWT (python-jose) + bcrypt — аутентификация

## Структура

```
main.py              точка входа, сборка роутеров, CORS
core/config.py       конфигурация, карта ORM-моделей
db/session.py        async engine и сессия SQLAlchemy
db/auth.py           JWT, хеширование паролей, проверка ролей
db/models/models.py  ORM-модели (22 таблицы)
routers/             7 роутеров, 33 эндпоинта
DB_SCRIPT.sql        схема, функции, процедуры, триггеры, справочники
test_validators.py   проверка контрольных сумм ISIN и ИНН
```

Роутеры разделены по ролям: `/api/public`, `/api/user`, `/api/broker`,
`/api/verifier`, `/api/staff`, `/api/admin`, `/charts`. Доступ к группе
эндпоинтов проверяется зависимостью на уровне роутера, а не в каждом
обработчике.

## Запуск

**1. Зависимости**

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

**2. Переменные окружения**

Скопируйте `.env.example` в `.env` и подставьте свои значения:

```bash
cp .env.example .env
```

| Переменная     | Назначение                                                  |
|----------------|-------------------------------------------------------------|
| `DATABASE_URL` | `postgresql+asyncpg://<user>:<password>@<host>:<port>/<db>` |
| `SECRET_KEY`   | ключ подписи JWT, например `openssl rand -hex 32`           |

Обе переменные обязательны: без них приложение не стартует. Значения по
умолчанию не предусмотрены намеренно, чтобы секрет не попал в репозиторий.

Загрузить `.env` в текущую сессию:

```bash
set -a && source .env && set +a
```

**3. Схема базы данных**

> **Внимание.** `DB_SCRIPT.sql` в начале удаляет **все** таблицы, последовательности,
> функции и процедуры в схемах, кроме системных. Выполняйте его только на отдельной
> базе, созданной под этот проект, иначе данные существующей базы будут потеряны
> без возможности восстановления.

```bash
createdb DB_Course
psql -d DB_Course -f DB_SCRIPT.sql
```

Скрипт создаёт схему и заполняет справочники: типы операций, статусы заявок,
уровни прав, валюты.

**4. Сервер**

```bash
python main.py
```

Документация API — http://localhost:8000/docs

## Тесты

`test_validators.py` проверяет реализованные в PL/pgSQL алгоритмы контрольных
сумм на эталонных значениях. Требуется применённая схема:

```bash
python test_validators.py
```

## Что реализовано на стороне БД

**Проверка реквизитов.** Контрольная сумма ISIN (расширение букв в цифры и
алгоритм Луна), контрольные цифры ИНН физического лица (12 знаков, две цифры) и
юридического лица (10 знаков), проверка БИК и паспортных данных. Бумага с
некорректным ISIN не попадёт в систему ни через один маршрут приложения.

**Денежные величины.** Все суммы — `NUMERIC(12,2)`, числа с плавающей точкой не
используются нигде.

**Жизненный цикл заявки.** Заявка на покупку резервирует средства на брокерском
счёте в момент подачи, заявка на продажу замораживает бумаги на депозитарном
счёте. При отклонении заявки выполняется компенсирующая операция: средства
возвращаются, бумаги размораживаются. Обе ветви ведут историю операций.

**Блокировки.** Изменение баланса выполняется после `SELECT ... FOR UPDATE` по
строке счёта, что исключает гонку при параллельной обработке заявок.

**Триггеры-инварианты.** Отрицательный баланс депозитарного и брокерского счёта
невозможен: попытка такой записи прерывается триггером.

**Архивация вместо удаления.** Снятие бумаги с торгов (`archive_security`)
сначала отклоняет все активные заявки по ней с возвратом средств владельцам, и
только затем помечает бумагу архивной. Записи не удаляются, история операций
остаётся целостной. Тот же подход применён к валютам.

## Ограничения

* Миграций нет: схема задаётся одним скриптом, который пересоздаёт базу целиком.
* В конце `DB_SCRIPT.sql` остались отладочные вызовы процедур, создающие тестовые
  заявки.
* Ряд процедур перехватывает `WHEN OTHERS` и возвращает `SQLERRM` текстом, что
  скрывает исходный тип ошибки.
* Автотестами покрыты только валидаторы контрольных сумм.
